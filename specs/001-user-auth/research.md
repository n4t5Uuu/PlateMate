# Research: User Authentication (Sign Up and Log In)

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md)

Sources: Clerk docs read on 2026-11-21 (pages named per decision), the installed packages in this repo (`@clerk/backend` 3.27.0 type definitions), and the Next.js 16 docs in `frontend/node_modules/next/dist/docs/`. Where the Clerk docs did not answer a question, that is stated and a verification step is added to [quickstart.md](quickstart.md). No unresolved clarifications remain; the open risks (R2, R11) are decided with a fallback and a check.

## R1. Use Clerk's prebuilt sign-in and sign-up components

- **Decision**: Build the log-in and sign-up pages with Clerk's `<SignIn />` and `<SignUp />` components on catch-all routes (`/sign-in/[[...sign-in]]`, `/sign-up/[[...sign-up]]`), styled to the product through their appearance options.
- **Rationale**: They already implement email and password, emailed links, Google and Microsoft, password reset, the second-factor prompt and session tasks. Writing these flows by hand would be far more code and more security surface (constitution III, simplicity). The Clerk quickstart describes `init`-generated sign-in and sign-up routes.
- **Alternatives considered**: Custom flows with the Clerk hooks (rejected: much more code, higher risk, no requirement needs them). A hosted Account Portal (rejected: the spec wants the pages inside PlateMate).
- **Not covered by the docs read**: the exact component props and catch-all route shape. Confirmed during the first task by reading the installed package types; fallback is the quickstart's generated routes.

## R2. Two-step verification through Clerk's "Require multi-factor authentication"

- **Decision**: Turn on the authenticator app (TOTP) and backup codes strategies, leave SMS off, and turn on **Require multi-factor authentication** in the Clerk Dashboard (Multi-factor page).
- **Evidence** (Clerk docs, sign-up and sign-in options, "Multi-factor authentication"): the supported methods are SMS code, authenticator app and backup codes; with the require toggle on, "after authenticating, users will have a pending `setup-mfa` session task and will need to fulfill the task before they are considered `active` (signed-in)". Enrollment generates backup codes (MFA recovery page). This matches FR-018, FR-019 and the "resume setup at next log-in" scenario.
- **Open risks, decided with a check** (verified in the quickstart's validation scenarios):
  1. **Plan**: MFA "requires a paid plan for production use, but you can try it for free in development mode". Needed before launch, not for building. Recorded as a launch dependency in the spec's assumptions.
  2. **Social sign-ins**: the docs do not say whether a required MFA policy challenges Google and Microsoft sign-ins. The Device Trust page says passwordless methods including OAuth are *not* affected by Device Trust, which is a different feature. Check in development with a Google account. If social sign-ins skip the second step, FR-020's "every method" cannot be met by configuration alone, and the user must choose: accept the provider's own protection for social sign-ins, or block social sign-in until Clerk supports it.
  3. **Disabling**: the docs do not say whether a user can remove their own second factor when MFA is required (the custom-flow page shows a remove action). Check in development. If it is possible, FR-021 needs a block, decided with the user.
- **Alternatives considered**: SMS codes (rejected: out of scope in the spec, SIM-swap risk). Our own TOTP implementation (rejected: security-sensitive code that Clerk already provides).

## R3. Deny by default at the front door

- **Decision**: A single `frontend/proxy.ts` runs `clerkMiddleware`. The only public routes are `/sign-in(/.*)?` and `/sign-up(/.*)?` (patterns that end at a path boundary; `/sign-in(.*)` would also make `/sign-in-evil` public, see "Confirmed from installed types"); every other route requires a session (`auth.protect()`). The list of public routes is one small exported helper so it can be unit-tested.
- **Rationale**: Next.js 16 names the file `proxy.ts` (Next docs, `01-app/01-getting-started/16-proxy.md`; Clerk quickstart: "proxy.ts on Next.js 16+"). A deny-by-default list means a forgotten new route is protected, which matches SC-004. The return-to-page behavior (FR-011) comes from Clerk's redirect handling; only same-site return addresses are honored.
- **Confirmed against the installed `@clerk/nextjs` types** (T004, see "Confirmed from installed types"): `createRouteMatcher` and `auth.protect()` behave as planned, but `createRouteMatcher` is marked `@deprecated` in 7.9.25.

## R4. Backend verifies the session with the installed `@clerk/backend`

- **Decision**: A Hono middleware in `backend/src/auth.ts` calls `createClerkClient(...).authenticateRequest(request)`, then `toAuth()` on the result, and answers 401 unless `toAuth().userId` is set. Checking only the result's `isAuthenticated` is not enough: it is `true` for a pending session (unfinished two-step setup), see "Confirmed from installed types". The frontend sends the session token as `Authorization: Bearer <token>`.
- **Evidence**: `@clerk/backend` 3.27.0 (already a backend dependency) exports `authenticateRequest` on the client (`dist/tokens/factory.d.ts`), whose result carries `isAuthenticated` and `toAuth()` (`dist/tokens/authStatus.d.ts`). A pending session still gets `isAuthenticated: true`; `toAuth()` returns the signed-out object for it by default (`treatPendingAsSignedOut` defaults to `true`).
- **Rationale**: No new dependency (constitution V). A bearer token avoids cross-origin cookie handling while the backend runs on a different port (8787) from the app (3000).
- **Alternatives considered**: `@hono/clerk-auth` (rejected: community package, new dependency). `@clerk/express` (rejected: wrong framework). Mounting the API inside the Next.js app so cookies work (rejected for now: separate issue #39).
- **Later option**: set a JWT verification key for networkless checks; not needed for this feature.

## R5. Users reach our database by webhook, with a just-in-time safety net

- **Decision**: `POST /webhooks/clerk` verifies the request with `verifyWebhook` from `@clerk/backend/webhooks` (signing secret from `CLERK_WEBHOOK_SIGNING_SECRET`) and applies `user.created`, `user.updated` and `user.deleted` through one idempotent `upsertUser` function. The authenticated-request middleware also calls `upsertUser` when it sees a Clerk user id that has no row yet.
- **Rationale**: The PRD says users are "synced from Clerk by webhook". Webhooks need a public address, which local development lacks, so the just-in-time upsert makes the feature work locally and covers a late or lost webhook (FR-014, SC-005: record within a minute, exactly once). One shared function keeps the two paths identical.
- **Alternatives considered**: Webhook only (rejected: cannot be tried locally, and a missed event loses the user). Just-in-time only (rejected: never sees profile changes or deletions).
- **Not covered by the docs read**: the webhook event payload shape. Parsed defensively with a Zod schema that keeps only the fields we store (constitution IV), and `verifyWebhook` returns a typed `WebhookEvent`.

## R6. What we store, and what Clerk keeps

- **Decision**: One new table, `users`, defined in `backend/db/src/schema.ts` (fields in [data-model.md](data-model.md)). Passwords, sessions, emailed-link tokens, second-factor secrets and backup codes live only in Clerk and are never copied.
- **Rationale**: Minimal data, no secrets in our database, and it follows the PRD data model. Deleting a person soft-deletes the row (`deleted_at`), as the PRD requires for history.

## R7. Calling the backend from the app, and CORS

- **Decision**: The frontend gets a session token with Clerk's `getToken()` and calls the backend with the bearer header. The backend allows the app's origin (`APP_URL`) through Hono's built-in `hono/cors`, with the `Authorization` header allowed.
- **Rationale**: Built in, no new dependency. A single private endpoint, `GET /me`, proves the whole chain (session, token, verification, user record) and feeds the signed-in home page.

## R8. Environment variables

- **Decision**: Names follow Clerk's environment variable page: `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY`, `NEXT_PUBLIC_CLERK_SIGN_IN_URL=/sign-in`, `NEXT_PUBLIC_CLERK_SIGN_UP_URL=/sign-up`, and the sign-in and sign-up fallback redirect URLs. The backend adds `CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY`, `CLERK_WEBHOOK_SIGNING_SECRET` and `APP_URL`. All are validated with Zod at startup, and `.env.example` documents them with empty values. Secrets are never committed (constitution quality gates).
- **Note**: the deprecated `NEXT_PUBLIC_CLERK_AFTER_SIGN_IN_URL` variables are not used.

## R9. Next.js 16 rendering rules

- **Decision**: `ClerkProvider` goes inside `<body>`, not around `<html>`. Because `cacheComponents: true` is on in `next.config.ts`, any server component that reads auth state (the header's sign-in and user controls, the home page) is wrapped in `<Suspense>`, and the catch-all sign-in and sign-up pages are wrapped too. `await auth()` always.
- **Rationale**: Stated in the Clerk quickstart's critical rules; without it `next build` fails.

## R10. Testing approach

- **Decision**: Jest unit tests (frontend and backend, in `frontend/tests/` and `backend/tests/`) for the logic that can be tested without a network or database: the public-route list, the authentication middleware (with Clerk's verification replaced by a stub), webhook payload parsing and email normalization. Behavior that needs the database or a real Clerk instance is covered by `pnpm smoke` additions and the manual validation in [quickstart.md](quickstart.md). Playwright end-to-end tests for the sign-in journey are deferred until the Playwright config and a CI database exist (GitHub issue #36).
- **Rationale**: Constitution II demands tests for permissions and validation and bans tests that depend on the network or local data. CI has no Postgres yet.

## R11. Time limits depend on what Clerk lets us configure

- **Decision**: The spec's defaults (5 failed attempts then a 15-minute block; 1-hour expiry for reset and emailed links; 30-day session, 7 days idle) are configured in the Clerk Dashboard where it allows.
- **Not covered by the docs read**: which of these Clerk exposes and in what steps. Verified when configuring the dashboard. If a value cannot be matched exactly, use the closest Clerk setting and update the spec's assumption (the spec already states these numbers are adjustable defaults).
## R12. Row-level security with Clerk as the identity source

- **Decision**: Always-on RLS on every data table (rule 1 of the project's security rules). Policies and the `platemate_app` role are declared in `backend/db/src/schema.ts` with Drizzle's `pgPolicy`, `pgRole` and `.enableRLS()` (present in the installed `drizzle-orm` 0.45.4), and applied by `pnpm db:push`. Because Clerk is not a database login, the backend passes identity per transaction through the transaction-local settings `app.clerk_user_id` and `app.actor` and runs the work as the non-owner role `platemate_app` with `set local role` (see [data-model.md](data-model.md)).
- **Rationale**: Postgres RLS is bypassed by the table owner, by superusers and by roles with `BYPASSRLS`, so request handlers must not run as those. `set_config(..., true)` is transaction-local, which is safe behind Neon's pooler. The Neon WebSocket driver already supports transactions (project stack), so the helper works for both Neon and the local postgres.js driver.
- **Alternatives considered**: A separate login role with its own connection string (cleaner, but needs role passwords and a second `DATABASE_URL`; kept as the upgrade path). `FORCE ROW LEVEL SECURITY` on tables (not exposed by Drizzle and unnecessary once handlers run as a non-owner). Neon Auth or Supabase-style `auth.uid()` (rejected: Clerk is the chosen provider). Application-only checks (rejected: the rule is that RLS is always enforced).
- **Open facts, verified before building on them** (spike in tasks): (1) Drizzle's `pgRole` supports `createRole`, `createDb` and `inherit` but not login or password, so the role is created without login and the owner assumes it with `set local role`; (2) whether the owner is allowed to `set role platemate_app` on both local Postgres and the Neon branch (newer Postgres versions do not grant that membership automatically when the owner creates a role, so a one-time `grant` may be needed, which is an infrastructure step, not a schema change); (3) that `drizzle-kit push` manages the role when `entities.roles` is set in `drizzle.config.ts`. If (2) fails, fall back to the separate login role.
- **Spike result (T005, Postgres 16.16 in Docker, everything in rolled-back transactions)**: the owner CAN assume the role, so R12 keeps `set local role platemate_app` and does not need the fallback. Open fact (1) holds: `create role platemate_app nologin nosuperuser nobypassrls` works for the owner. Open fact (2): on the local database the owner (`platemate`) is a superuser, so `set local role` works with no grant (superusers may assume any role; `pg_auth_members` stays empty). Neon's owner is not a superuser, and the spike shows what happens then: a role with `CREATEROLE` that creates the role gets only `admin_option` (`inherit_option` and `set_option` are false) and `set role` fails with `permission denied to set role`. After `grant platemate_app to <owner> with set true` it works. So **T010 must run that one-time grant on any non-superuser owner (the Neon branches)**; it is an infrastructure step (a line in the setup docs or a migration step), not a table change, and it is harmless on a superuser owner. With the role assumed: the owner's `select` sees every row (bypasses RLS); as `platemate_app` with no `app.clerk_user_id` set, a `select` returns 0 rows (`current_setting(..., true)` gives null); with it set, only that person's row; an `update` of another person's row changes 0 rows; an `update` that moves a row to another `clerk_user_id` and an `insert` for another person both fail with `new row violates row-level security policy`; a `delete` with no delete policy removes 0 rows, and the owner still saw both rows afterward. Not verified by the spike: open fact (3), that `drizzle-kit push` manages the role through `entities.roles`; T010 checks it.
- **Local environment catch**: a native Windows Postgres service also listens on host port 5432 next to Docker's. From the host, `localhost:5432` with `platemate:platemate` failed with `password authentication failed`, so the host connection reaches the wrong server and not the Docker container (checked with `netstat` and the process list). The spike therefore ran through `docker exec ... psql` inside the container instead of the `postgres` package. Anyone running `pnpm dev`, `pnpm db:push` or `pnpm db:verify-rls` from the host needs that native service stopped, or the container published on another port, before the local database works.
- **T010 grants** (one-time infrastructure step, not expressible in `schema.ts`: drizzle-kit emits no `GRANT`, and `pgRole`/`pgPolicy` have no grant option; checked by T010 with `drizzle-kit export`, which creates the role, the table, `ENABLE ROW LEVEL SECURITY` and the three policies and nothing else). After `pnpm db:push`, run once per database as the owner, in this order: `grant select, insert, update on users to platemate_app;` (never `delete`, and `usage` on the schema is already there through `public`), then, on a non-superuser owner such as the Neon branches, `grant platemate_app to <owner> with set true;`. Both are harmless to repeat; on the local superuser owner only the first is needed. A later table needs its own `grant` line. Without them `set local role platemate_app` fails (Neon) or every query fails with `permission denied for table users`. `db:verify-rls` (T013) must fail when the table privileges or the membership are missing, and the setup docs must list both lines.
- **`drizzle-kit push` drops policy conditions (found 2026-11-25 by the first real `db:verify-rls` run on the local Docker database)**: with drizzle-kit 0.31.11, `push` runs `CREATE POLICY "users_select" ON "users" AS PERMISSIVE FOR SELECT TO "platemate_app";` with no `USING` or `WITH CHECK`, while `drizzle-kit export` prints the full conditions for the same schema. Postgres then stores policies with empty conditions (`pg_policies.qual` and `with_check` are empty), so nothing matches: a person sees 0 rows and the sync actor cannot read or insert. It fails closed (no leak), but the policies do not do what `schema.ts` says. Reproduced on a throwaway database, which was dropped. `db:verify-rls` caught it ("a person sees only their own row: saw 0 rows", "the sync actor can upsert"). Whether the generated-migration path (`db:generate`, `db:migrate`) keeps the conditions is NOT yet tested.
- **Webhook writes**: the sync runs with `app.actor = 'clerk-sync'`, set only inside the webhook handler. This protects against missing-`WHERE` bugs, not against code that deliberately sets the actor, and that limit is documented in code with a `shortcut:` comment.

## R13. Cross-site scripting (XSS) defenses for this feature

- **Decision**: (a) React's default escaping everywhere, with `react/no-danger` set to `error` in `frontend/eslint.config.mjs`; (b) a Content-Security-Policy and companion headers (`X-Content-Type-Options: nosniff`, `Referrer-Policy`, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, no `unsafe-eval`) built in one tested function in `frontend/lib/security-headers.ts` and applied through `headers()` in `frontend/next.config.ts`, starting in report-only mode and enforced once the sign-in pages work under it; (c) the one user-controlled value this feature shows, the person's name, is rendered as text only, and a test with a script-like name proves it.
- **Rationale**: Matches rule 3 of the project's security rules. A static header set avoids the dynamic rendering that nonces would force on `cacheComponents` pages.
- **Not covered by the docs read**: the exact origins Clerk's components need in `script-src`, `connect-src`, `img-src` and `frame-src`. The task reads Clerk's content-security-policy guidance first and adds only what it lists; if a static policy cannot allow Clerk without `unsafe-inline`, switch to a nonce-based policy in `proxy.ts` and record the trade-off here.
- **Origins and trade-off (T020, read 2026-11-25)**: Clerk's content-security-policy guide (clerk.com/docs/guides/secure/best-practices/csp-headers, fetched through a summarizing tool, so the exact values are VERIFIED only to that extent; they match the defaults in the installed `@clerk/nextjs` `server/content-security-policy.js`) lists: `script-src` the Frontend API host (from the publishable key; both `clerk.browser.js` and `ui.browser.js` load from it), `https://challenges.cloudflare.com`, `https://*.protect.clerk.com`; `connect-src` the Frontend API host and `https://*.protect.clerk.com:*` (the port is required); `img-src https://img.clerk.com`; `frame-src` Cloudflare and `*.protect.clerk.com`; `style-src 'unsafe-inline'`; `worker-src 'self' blob:`. `frontend/lib/security-headers.ts` uses Clerk's origins above plus these PlateMate defaults that are not from Clerk's guide: `default-src 'self'`, `font-src 'self'`, `form-action 'self'` (can block redirects after a form submit in Chrome, check it at T062), `'self'` in `style-src`, `img-src` and `connect-src`. The policy therefore does not allow the sign-in pages' own backend calls, Clerk telemetry (`clerk-telemetry.com`, in Clerk's own defaults but not in its guide) and Stripe origins are not allowed. The Frontend API host is derived from `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` when `headers()` runs.
- **Static policy cannot be enforced as is**: Clerk's guide says `'unsafe-inline'` in `script-src` is required on the App Router unless the strict-dynamic (nonce) approach is used, and Next's own bootstrap is inline too (the built `/sign-in` HTML has 4 inline `<script>` tags). The T019 policy deliberately omits `'unsafe-inline'`, so it is report-only and will report those inline scripts; it must not be enforced as is. T062 may only enforce after one of: (a) accept `'unsafe-inline'` in `script-src` (weakens the XSS defense this policy exists for), or (b) the nonce policy in `frontend/proxy.ts` (T037): `clerkMiddleware(..., { contentSecurityPolicy: { strict: true } })` makes a per-request nonce with `'strict-dynamic'`, passes it to `<ClerkProvider dynamic>` (the `dynamic` prop is required), and requires every page to render at request time. Next's CSP guide says Partial Prerendering is incompatible with nonces, so with `cacheComponents` on every page would need a dynamic boundary (Clerk suggests `<Suspense>` plus `connection()`), which costs the static shell; or (c) Next's experimental hash-based Subresource Integrity (Next's CSP guide, "Subresource Integrity (Experimental)"), which keeps static generation under a strict policy; not tested with Clerk's loader. Decide at T062 with the Scenario 9 results.
- **Alternatives considered**: A sanitizer library for names (rejected: names are plain text, escaping is enough and adds no dependency). Skipping CSP until later (rejected: the project's rules require it).

### Corrections to earlier statements (already fixed above)

1. **R3 public patterns.** `/sign-in(.*)` also matches `/sign-in-evil`. Run against `@clerk/shared` `createPathMatcher` (`pathMatcher.js`): `/sign-in(.*)` matches `/sign-in-evil`, while `/sign-in(/.*)?` and `/sign-in/:path*` do not, and both still match `/sign-in`, `/sign-in/factor-two` and `/sign-in/tasks/setup-mfa`. R3 now uses `/sign-in(/.*)?` and `/sign-up(/.*)?`, as T036 already did.
2. **R4: `isAuthenticated` is not enough.** `signedIn()` in `@clerk/backend` sets `isAuthenticated: true` for every verified session token, including a **pending** one (unfinished two-step setup). Only `toAuth()` applies `treatPendingAsSignedOut` (default `true`) and returns a signed-out object for it. R4 and T038 must check `state.toAuth().userId`, not `state.isAuthenticated`. Evidence: `tokens/authStatus.d.ts` (`AuthenticatedState.isAuthenticated: true`, `toAuth: ToAuth<T, true>` taking `PendingSessionOptions`), `@clerk/shared` `types/session.d.ts` (`PendingSessionOptions.treatPendingAsSignedOut`, `@default true`), and the `signedIn` function in `@clerk/backend` `index.js` (`toAuth` returns `signedOutAuthObject(void 0, authObject.sessionStatus)` when `sessionStatus === "pending"`).
3. **T004's pointer to `authObjects.d.ts`.** That file mentions `treatPendingAsSignedOut` only on the `@internal` `getAuthObjectFromJwt`. The option a request handler uses is on `toAuth()` (above). It is not an option of `authenticateRequest`, nor of `clerkMiddleware`'s options.
4. **`createRouteMatcher` is deprecated** in 7.9.25 (`server/routeMatcher.d.ts`: `@deprecated This function will be removed in the next major version`; the `.js` calls `deprecated(...)`, which does `console.warn`). It still works, so the plan stands; it is a known limit, not a defect. Upgrade path if it is removed: a plain `RegExp` list or function in `frontend/lib/auth-routes.ts`, tested the same way.

### `createRouteMatcher` and `auth.protect()` (`@clerk/nextjs/server`)

- `createRouteMatcher(routes: RouteMatcherParam) => (req: NextRequest) => boolean` (`types/server/routeMatcher.d.ts`, exported from `types/server/index.d.ts`). `RouteMatcherParam` is a pattern string, a `RegExp`, an array of them, or a `(req) => boolean` function.
- The string form is path-to-regexp style; `(.*)` is not boundary-safe (correction 1). The matcher normalizes the path first (`normalizePath` in `@clerk/shared` `pathMatcher.d.ts`: `decodeURI`, then collapse `//`), and throws `MalformedURLError` (status 400) on bad percent-encoding, which `clerkMiddleware` turns into a 400 (`esm/server/clerkMiddleware.js`, `isMalformedURLError`).
- `auth.protect` is on `ClerkMiddlewareAuth = AuthFn` (`types/server/clerkMiddleware.d.ts`, `types/app-router/server/auth.d.ts`); signature in `types/server/protect.d.ts`. `await auth.protect()` returns the `SignedInAuthObject`, or throws a control-flow error that `clerkMiddleware` converts into a response. Options: `{ token?, unauthorizedUrl?, unauthenticatedUrl? }`.
- When not signed in (`types/server/protect.d.ts` comments, `esm/server/protect.js`): a page request is redirected to sign-in, a server action gets 401, any other request (an API call) gets 404. `unauthenticatedUrl` overrides the redirect.
- A **pending** session counts as not signed in: `createProtect` checks `authObject.sessionStatus === "pending"` and takes the unauthenticated path (`esm/server/protect.js`). In the proxy the redirect is built with the session's status, and `createRedirect` in `@clerk/backend` then sends a pending session to `<signInUrl>/tasks` instead of `<signInUrl>` (`chunk-CSXNUYCW.mjs`, `redirectToTasks`). So `/sign-in/tasks/...` must be public, which `/sign-in(/.*)?` covers.
- Inside the proxy, `auth()` and `auth.protect()` use the default `treatPendingAsSignedOut: true`. For T037's "signed-in person on `/sign-in` goes to `/`": `await auth()` gives `userId: null` for a pending session, so a person in the middle of setup is not bounced away from it. Do not pass `treatPendingAsSignedOut: false` there.
- Dev-only trap (`esm/client-boundary/hooks/useEnforceCatchAllRoute.js`): in development `<SignIn />` fetches `<path>/SignIn_clerk_catchall_check_<time>` and throws "not configured correctly" if the answer is 404 or the proxy protects it. The route must be a real catch-all and the proxy must not protect anything under it.

### `<SignIn />` and `<SignUp />` props, and session tasks

- Next's `SignIn` and `SignUp` take the props of the `@clerk/react` components (`types/client-boundary/uiComponents.d.ts`). The props are in `@clerk/shared` `types/clerk.d.ts`:
  - `SignInProps = RoutingOptions & { forceRedirectUrl, fallbackRedirectUrl, signInUrl, signUpUrl, appearance, initialValues, waitlistUrl, unsafeMetadata, withSignUp, oauthFlow, oidcPrompt, transferable, signUpForceRedirectUrl, signUpFallbackRedirectUrl, afterSignOutUrl, __experimental }`.
  - `SignUpProps = RoutingOptions & { forceRedirectUrl, fallbackRedirectUrl, signInUrl, appearance, unsafeMetadata, initialValues, waitlistUrl, oauthFlow, oidcPrompt, signInFallbackRedirectUrl, signInForceRedirectUrl, afterSignOutUrl, __experimental }`.
  - Everything is optional except the routing choice below.
- `RoutingOptions` is `{ path: string | undefined; routing?: 'path' } | { path?: never; routing?: 'hash' }`. In Next, `path` is filled in: `useEnforceCorrectRoutingProps` computes it from the URL minus the catch-all segment (`esm/client-boundary/hooks/useEnforceRoutingProps.js`, `usePathnameWithoutCatchAll.js`). On `/sign-in/[[...sign-in]]` no `path` prop is needed.
- Redirects: the env names in R8 are read by `esm/utils/mergeNextClerkPropsWithEnv.js` (`NEXT_PUBLIC_CLERK_SIGN_IN_URL`, `..._SIGN_UP_URL`, the `..._FALLBACK_REDIRECT_URL` pair, and `..._FORCE_REDIRECT_URL` variants). From the doc comments in `SignInProps`: `forceRedirectUrl` beats other redirect props, env variables and search params; `fallbackRedirectUrl` is used only when none of those is present. So, to keep return-to-page (FR-011), use the fallback and never the force variant. Whether Clerk restricts return addresses to the same site: not found in the types.
- Session tasks: the keys are `'choose-organization' | 'reset-password' | 'setup-mfa'` (`@clerk/shared` `types/session.d.ts`, `SessionTask.key`). A session with an unfinished task has `sessionStatus` `'pending'`.
- How tasks are rendered: **neither `SignIn` nor `SignUp` has a task prop.** What exists in the types:

### `authenticateRequest` and `treatPendingAsSignedOut` (`@clerk/backend`)

- `createClerkClient(...).authenticateRequest(request: Request, options?)` returns `Promise<RequestState>` (`tokens/request.d.ts`, `tokens/factory.d.ts`). `options` is `AuthenticateRequestOptions` (`tokens/types.d.ts`: `publishableKey`, `secretKey`, `jwtKey`, `acceptsToken`, `authorizedParties` and more, the last through `& VerifyTokenOptions`). `acceptsToken` defaults to `'session_token'`, which is what we want.
- The `Authorization: Bearer <token>` header is read (`chunk-CSXNUYCW.mjs`, `parseAuthorizationHeader`, scheme `Bearer`), so R4's bearer approach is supported.
- `RequestState` is `AuthenticatedState | UnauthenticatedState | HandshakeState` (`tokens/authStatus.d.ts`), with `status` `'signed-in' | 'signed-out' | 'handshake'`. A `handshake` state has `toAuth: () => null`; a bearer-token API call should not produce it, but `requireAuth` must answer 401 for anything that does not give a `userId` and must not call `toAuth()` on a handshake state (check `status` first).
- `toAuth(opts?: PendingSessionOptions)` is on the signed-in state; `PendingSessionOptions = { treatPendingAsSignedOut?: boolean }`, default `true` (`@clerk/shared` `types/session.d.ts`). For the pending case the result is a `SignedOutAuthObject` with `userId: null` and `sessionStatus: 'pending'` (`tokens/authObjects.d.ts`).
- `authorizedParties?: string[]` ("an allowlist of origins to verify against, to protect your application from the subdomain cookie leaking attack", `jwt/verifyJwt.d.ts`) is accepted by `authenticateRequest`. Whether to set it to `APP_URL` is a decision for the user and is not made here; not found: whether session tokens fetched with `getToken()` always carry the `azp` claim it checks.

### `WebhookEvent` and `verifyWebhook` (`@clerk/backend/webhooks`)

- `verifyWebhook(request: Request, options?: { signingSecret?: string }): Promise<WebhookEvent>` (`webhooks.d.ts`); the `./webhooks` export is declared in `@clerk/backend/package.json`. With no `signingSecret` it falls back to the `CLERK_WEBHOOK_SIGNING_SECRET` environment variable (`webhooks.mjs`); pass it explicitly from `backend/src/env.ts`.
- It reads the headers `svix-id`, `svix-timestamp` and `svix-signature` and consumes the body with `request.text()`, so pass the raw request (`c.req.raw`) and read nothing from it first. On a missing secret, a missing header or a failed signature it **throws** (`webhooks.mjs`); the route must catch it and answer 400.
- Shape (`api/resources/Webhooks.d.ts`): `WebhookEvent` is a union of `Webhook<Type, Data>` = `{ type, object: 'event', data, event_attributes: { http_request: { client_ip, user_agent } }, timestamp: number, instance_id: string }`. For users: `UserWebhookEvent = Webhook<'user.created' | 'user.updated', UserJSON> | Webhook<'user.deleted', UserDeletedJSON>`.
- `UserJSON` (`api/resources/JSON.d.ts`) has `id: string` (from `ClerkResourceJSON`), `first_name: string | null`, `last_name: string | null`, `image_url: string`, `primary_email_address_id: string | null` and `email_addresses: EmailAddressJSON[]`, where `EmailAddressJSON` has `id: string` and `email_address: string`. Those are exactly the fields T007 lists. Three of them can be `null`, so the Zod schema must allow `null` on them.
- `UserDeletedJSON extends DeletedObjectJSON` is `{ object: string; id?: string; slug?: string; deleted: boolean; external_id?: string }`. **`id` is optional on a deleted event**, so the `user.deleted` schema must reject a missing id instead of assuming one.
- `data` is the parsed JSON returned as is, not checked at run time (`webhooks.mjs` returns `payload.data`), so the Zod parse in T007 is needed and not redundant.

### Drizzle: `pgRole`, `pgPolicy`, `.enableRLS()` (`drizzle-orm` 0.45.4, `pg-core/`)

- `pgRole(name, config?: { createDb?, createRole?, inherit? })` and `PgRole.existing()` (`roles.d.ts`). There is no login, password, superuser or `BYPASSRLS` option. In drizzle-kit, `inherit` defaults to `true` when unset, and the statement is `CREATE ROLE "name"` plus `WITH CREATEDB`, `CREATEROLE` or `NOINHERIT` only when those are asked for (`bin.cjs`, `PgCreateRoleConvertor`). Postgres' own defaults then apply: `NOLOGIN NOSUPERUSER NOBYPASSRLS`. A role marked `.existing()` is skipped by the generator. The role must be a named export of `schema.ts` (drizzle-kit collects exports with `is(t, PgRole)`).
- `pgPolicy(name, { as?: 'permissive' | 'restrictive', for?: 'all' | 'select' | 'insert' | 'update' | 'delete', to?, using?: SQL, withCheck?: SQL })` (`policies.d.ts`). `to` accepts a `PgRole`, a role name, `'public'`, `'current_user'` and so on, or an array. A policy goes in the table's third argument: `PgTableExtraConfigValue` includes `PgPolicy` (`table.d.ts`). The `current_setting('app.clerk_user_id', true)` expressions go through the `sql` tag.
- `.enableRLS()` is on `PgTableWithColumns` (`table.d.ts`: `enableRLS: () => Omit<PgTableWithColumns<T>, 'enableRLS'>`) and sets the `EnableRLS` symbol (`table.js`). drizzle-kit also emits `ENABLE ROW LEVEL SECURITY` by itself once a table has a policy (`bin.cjs`: `enable_rls` when the table gains policies), so `.enableRLS()` is redundant for `users` and the only switch for a table that has no policy yet. Keep it: it states the intent and `db:verify-rls` checks the result either way.
- **No `GRANT` is generated.** Searching `bin.cjs` for `GRANT` finds nothing; drizzle-kit emits `CREATE POLICY ... TO "platemate_app"` only. A policy filters rows but does not give the role table privileges, so `platemate_app` needs `grant select, insert, update on users to platemate_app`, as part of the same one-time infrastructure step as the `set role` membership grant in R12. The T005 result does not say how table access was given in the spike, so T010 must add this grant to that step, and `db:verify-rls` should fail when it is missing. Not found in the installed packages: any Drizzle way to declare grants.

### `entities.roles` in `drizzle.config.ts` (`drizzle-kit` 0.31.11)

- The option exists (`index.d.ts`): `entities?: { roles?: boolean | { provider?: 'supabase' | 'neon' | string; exclude?: string[]; include?: string[] } }`.
- **`roles: true` is unsafe here.** With it, introspection reads every role in the database (`bin.cjs`: `SELECT rolname, ... FROM pg_roles`), and a role that exists in the database but not in `schema.ts` becomes `DROP ROLE "..."` (`PgDropRoleConvertor`, `deletedRoles`). That list includes the database owner role. Use the allow-list form, `entities: { roles: { include: ['platemate_app'] } }`, which reads only that role. `provider: 'neon'` only excludes `authenticated` and `anonymous`, so it is not a substitute. T009 and T010 must use `include`.
- Open fact (3) in R12 is therefore settled on the config side: the option exists and the allow-list form manages exactly one role. Whether `pnpm db:push` creates it without error on the local and the Neon database is still checked by T010 at run time.
