# Data Model: User Authentication

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Research**: [research.md](research.md)

Only one table is added. The spec's **Session** and **Two-step verification** entities, and the **Sign-in method**, are owned by Clerk and are not stored in PlateMate's database (see R6 in research.md).

## Schema overview

Everything for sign-in is defined in `backend/db/src/schema.ts` and applied with `pnpm db:push` (never hand-written SQL):

| Object | Kind | Purpose |
| --- | --- | --- |
| `platemate_app` | Database role | The role every request handler runs as. Not the table owner, no `BYPASSRLS`, so row-level security applies to it. |
| `users` | Table, RLS on | The person's record, synced from Clerk. |
| `users_select`, `users_insert`, `users_update` | Row-level security policies | Who can read, create and change rows. There is deliberately **no delete policy**, so rows can never be hard-deleted through the app. |

Clerk owns identities, credentials, sessions and second-factor data. Nothing secret is stored here. Later features add tables (workspaces, projects and so on), and every one of them must follow the same rules in "Row-level security" below.

## users (new, in `backend/db/src/schema.ts`)

Follows the PRD data model: "People, synced from Clerk".

| Field | Type | Rules |
| --- | --- | --- |
| `id` | uuid | Primary key, generated by the database. This is the id other tables will reference. |
| `clerk_user_id` | text | Required, unique, not editable. The stable link to the Clerk account (looks like `user_...`). |
| `email` | text | Required. Stored lowercased and trimmed. Unique among rows that are not deleted. The person's primary verified email. |
| `name` | text | Nullable. Display name, built from first and last name when Clerk has them. Never invented. |
| `avatar_url` | text | Nullable. The profile image address from Clerk. |
| `created_at` | timestamp with time zone | Required, defaults to now. |
| `updated_at` | timestamp with time zone | Required, set on every sync. |
| `deleted_at` | timestamp with time zone | Nullable. Set when Clerk reports the account deleted (soft delete; the PRD forbids hard deletes of history). |

**Why these fields**: they are exactly what the spec's **User** entity needs (unique verified email, display name when available, creation date) plus the Clerk link and avatar the PRD lists. Nothing secret is stored.

### Row-level security (always on)

Row-level security (RLS) is enabled on `users`. **Default deny**: a role with no matching policy sees and changes nothing. Clerk is not a database login, so the database learns who is calling from two settings that the backend sets **inside each transaction** (transaction-local, so they cannot leak between pooled connections):

- `app.clerk_user_id`: the verified Clerk user id of the signed-in person.
- `app.actor`: set to `clerk-sync` only by the webhook handler, for the automatic sync.

| Policy | Applies to | Rule (`current_setting(..., true)` is null when unset, which denies) |
| --- | --- | --- |
| `users_select` | `platemate_app`, select | `clerk_user_id = current_setting('app.clerk_user_id', true)` **or** `current_setting('app.actor', true) = 'clerk-sync'` |
| `users_insert` | `platemate_app`, insert | `with check`: the same condition, so a person can create only their own row (the just-in-time sync) and the webhook can create any |
| `users_update` | `platemate_app`, update | `using` and `with check`: `current_setting('app.actor', true) = 'clerk-sync'` only. A person cannot edit their own record in this feature; profile editing comes later with its own policy |
| (none) | delete | No policy, so nothing can be deleted. Removal is the soft delete `deleted_at`, written by the sync |

**How the app uses it**: a helper in `backend/db/src/with-context.ts` opens a transaction, runs `set local role platemate_app`, sets the context with parameterized `set_config(..., true)` calls (never string-built SQL), then runs the work. Request handlers always go through it; they never query the bare connection.

**Limits, recorded as a shortcut**: the connection itself is the table owner (it runs migrations), and the app drops to `platemate_app` per transaction. A bug that forgets the helper would run as the owner and bypass RLS, so the check script and review look for bare queries. Upgrade path: a separate login role for the app with its own connection string, when the Neon dev and production branches exist (issue #37).

**Immutable `clerk_user_id`**: RLS cannot lock a single column. The code never updates it, and the update policy's `with check` refuses rows that move to another person.

**The always-RLS gate**: `pnpm db:verify-rls` (local database only) proves, as `platemate_app` inside a rolled-back transaction, that with no context nothing is visible, a person sees only their own row, cannot create or edit another person's, cannot delete, and the sync actor can upsert. It also fails if **any table in the public schema has RLS switched off**, so a new table cannot be added without policies.

### Relationships

None yet. Later features add `workspace_members.user_id`, `project_members.user_id`, `plate_versions.uploaded_by` and similar columns that reference `users.id`.

### Validation rules (from the spec)

- One account per person (FR-006): `clerk_user_id` unique, and `email` unique among live rows. Clerk links several sign-in methods with the same verified email to one Clerk user, so one Clerk user maps to one row.
- Exactly once and without manual steps (FR-014, SC-005): the write is an upsert keyed by `clerk_user_id`, so a webhook and a just-in-time write for the same person produce one row.
- Capitalization (edge case): emails are lowercased before storing and comparing.

### State transitions

```text
(no row) --user.created webhook or first authenticated request--> active
active   --user.updated webhook--> active (name, email, avatar refreshed, updated_at set)
active   --user.deleted webhook--> deleted (deleted_at set; row kept)
deleted  --same clerk_user_id seen again--> stays deleted; the person cannot log in because Clerk no longer has the account
```

An event that arrives out of order or twice changes nothing it should not: `user.updated` for an unknown person creates the row, and `user.deleted` for an unknown person does nothing.
